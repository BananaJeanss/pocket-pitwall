# Wear OS architecture

Pocket Pitwall keeps one repository for the phone app, the Wear OS app and
the code they share. The phone stays the canonical session store and the
primary analysis pipeline; the watch is a reliable, independent sensor logger.

```
Galaxy Watch (Wear OS, :wear)
  accelerometer · gyroscope · rotation vector · heart rate (optional)
  local raw log (WatchLogCodec "PWTCH" binary, CRC-protected)
        |  MessageClient  "/pitwall"   control plane (JSON, versioned)
        |  ChannelClient   log transfer  data plane (binary, acked)
        v
Android phone (:app)
  existing phone IMU/session pipeline (unchanged)
  clock alignment (ClockSync) · watch-log import (idempotent)
  fusion + derived telemetry · canonical session storage
  export/review/backup (unchanged for phone-only sessions)
        |  MessageClient "/pitwall"    compact result summary
        v
Galaxy Watch
  post-session status/results screen
```

## Modules

| Module | Kind | Contents |
| --- | --- | --- |
| `:app` | Android app (phone) | Existing app plus watch coordination, import and result-push features. |
| `:wear` | Android app (Wear OS) | Watch logger app: sensors, recorder service, local log store, transfer queue, glanceable UI. |
| `:protocol` | pure Kotlin/JVM | Shared domain/protocol code: JSON, control messages, WatchLog binary codec, clock-sync math, wrist/steering analysis. No Android dependencies. |
| `:core` | pure Java | Existing lap/sector analysis. Unchanged. |

Why a new `:protocol` module instead of extending `:core` (issue #16 asked
for either): `:core` is pure Java with a javac-only test harness
(`scripts/test-core.sh`), kept deliberately dependency-free. The watch/phone
shared code is Kotlin, needs its own test runner (kotlin.test), and adding it
to `:core` would have forced either Kotlin into the javac harness or JSON
parsing into Android's `org.json`. A separate module keeps both test harnesses
and both dependency philosophies intact, and mirrors the boundary the issue
asked for ("small pure Kotlin/shared module instead of duplicating models").

## Control protocol (Data Layer)

All control messages flow over a single MessageClient path `/pitwall`, encoded
as UTF-8 JSON via `PitwallJson` (identical code on both devices; wire
compatibility is enforced by one shared unit-test suite). See
`Messages.kt` for the full list: hello, start, startAck, stop, stopAck,
status, syncPing, syncPong, result, transferAck.

Design rules:

- **Versioned**: every message carries the sender's `PROTOCOL_VERSION`.
  Unknown types decode to `Messages.Unknown` and are ignored — a newer phone
  must not break an older watch.
- **Session-scoped**: every session-scoped message carries the session UUID
  generated by the phone, so watch data can never attach to the wrong drive.
- **Idempotent**: start/stop are tied to a sequence number; replays are acked
  again but never duplicated.
- **Phone is canonical**: the watch derives nothing authoritative; it records
  raw data and displays the phone's compact results.

Data-layer app identity requirement: the watch APK uses the same
`applicationId` (`dev.bananajeans.pitwall`) as the phone APK and both must be
signed with the same key (release signing reuses the phone keystore), which is
Google's requirement for phone/watch Data Layer communication without a
Play-Console app-linking step.

## Watch log format ("PWTCH")

`WatchLogCodec` writes incrementally-appended, individually CRC-32-protected
frames, and finalizes with a trailer carrying a payload CRC and length. Key
properties (issue #18/#21):

- **No lossy resampling**: raw monotonic nanosecond timestamps are preserved
  (delta-coded per sensor stream).
- **Crash-safe**: a file without a valid trailer is INCOMPLETE; complete
  frames before the corruption point are still recovered and the reason is
  surfaced to consumers. A corrupted byte in a finalized log can never
  surface as COMPLETE.
- **Compact**: 28 bytes/sample (versus 60+ for CSV/JSON lines) with values
  scaled by 1e6 into i32 (saturating beyond ±2147, far outside IMU ranges).
- **Self-describing**: header metadata (JSON) carries session id, watch app
  version, device model, start timestamps, sensor capabilities and protocol
  version.

## Clock synchronization

`ClockSync` turns repeated SyncPing/SyncPong exchanges into a linear mapping
between the watch and phone monotonic clocks (NTP-style offset + drift fit
with MAD-based RTT outlier rejection). The phone timeline is canonical:
watch samples are mapped into it with `phoneFromWatch`. Sync quality
(EXCELLENT/GOOD/POOR/NONE, residual RMS, best RTT) is persisted with the
imported stream, and analysis must refuse to claim sub-frame precision when
quality is poor.

## Session data model

The phone session (JSON `schemaVersion 1`) is extended with an optional
`watch` object. Phone-only sessions (existing installs) have no `watch` key
and load exactly as before. When present it records device metadata, sensor
capabilities, observed sample rates, sync mapping/quality, transfer/import
status and a link to the raw imported log. Derived watch metrics live in the
same object so they can be recomputed when analysis is re-run.

## Failure semantics

- Watch recording never depends on connectivity; disconnects during a session
  leave the local log intact.
- Completed logs stay queued on the watch until the phone acks durable import
  (`transferAck`); delivery is idempotent by session id.
- The phone session is never blocked by the watch: missing watch data is a
  first-class state, not an error.
